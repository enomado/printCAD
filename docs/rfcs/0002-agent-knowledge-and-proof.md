# RFC 0002: What an agent knows, and how it proves its work

- Status: in progress; milestone 1 built (the contract, its runner and the
  reference, a first batch of notes and two recipes; the Surface
  commands' notes still to come)
- Date: 2026-10-06
- Scope: `core_document::command` (the command contract), the `agents`
  crate, `app_shell` (`app/mcp.rs`, `app/agent_context.rs`,
  `app/scripts.rs`, `thumbnail.rs`, `headless.rs`), the benches'
  command registrations, `bench_api` (package commands), docs

## Summary

An AI agent drives printCAD through its commands (`call`, `lua`). Today
it learns them from a one-line summary and a list of arguments, and it
checks its work with a picture of whatever the user's camera shows. This
RFC gives it four things:

1. **Notes, examples and recipes for commands, checked by tests.** What
   a command does beyond its arguments: what it refuses, what it does
   silently, the mistakes agents make with it, and a working example.
   Every example runs in the test suite, so a note cannot drift from what
   the command does.
2. **Discovery tools.** `search` (ranked, with CAD synonyms) and
   `describe` (one or many commands or documents, typo-tolerant), and a
   compact index of every command in the instructions, in place of the
   whole list at once.
3. **A renderer for proof.** The `view` tool takes a view (iso, front,
   top…, or any direction), frames what it is asked to show, and draws
   edges, highlights, markers and a section, the same picture every time
   for the same input, independent of the user's camera.
4. **Script-first work.** The instructions steer multi-step work to one
   `lua` script that computes, loops and filters geometry; scripts
   return a value; geometry queries hand faces and edges onward as
   points and directions in world space.

## Motivation

The Surface workbench test of 2026-10-06 was made by an agent through
the MCP server, 16 commands, every case checked by measurement. Most of
what it found was not a wrong shape but an agent working blind:

- a step with no inputs built nothing and said nothing;
- `direction = "Custom"` without its numbers failed with a deserializer's
  message;
- a fillet across unsewn sheets failed with a kernel message that did
  not say to sew first;
- `surface.check` and Create sketch had no command, so the agent could
  not reach them, and `pc.sketch.new{body = …}` (which does the latter)
  was not discoverable from the surface commands;
- face names came back as floats, losing precision;
- every check of a shape was a measurement or a picture from the user's
  camera, which may look at something else.

Some of these were fixed in the commands themselves. The rest is
knowledge: what a command expects, refuses and does without saying, and
which other command does the related thing. An agent finds it today
only by failing. Each failure is a tool call, a turn, tokens, and a step
the user watches go wrong.

Meanwhile the whole reference (`docs/SCRIPTING.md`, 245 commands, about
91 KB) is one resource an agent must read in full to search it, and
`commands` returns every command at once, more than an agent wants in a
turn and growing with every bench and package.

## Goals

- An agent finds the command for a task in one call, by the words a
  user would use ("hole", "round", "shell"), not only by id.
- Every command an agent can run says what it refuses and what it does
  silently, with an example that works today.
- Notes and examples are checked by tests, and the test suite fails when
  a command's behaviour drifts from its documentation.
- An agent can look at a body, a set of faces or a section from a fixed
  view and know the picture shows what it asked about.
- Multi-step work takes one script, not one call per step.
- Packages (RFC 0001) can document their commands the same way.

## Non-goals

- An in-app agent that calls model APIs directly (a separate RFC, needed
  for a web build where no agent program runs).
- Sharing a session beyond the machine.
- Replacing `docs/SCRIPTING.md`: it stays the generated reference for
  people; the notes extend it.
- Visual regression testing of the viewport.

## Background: what an agent has today

- **Commands.** `CommandSpec` (`core_document::command`): `id`,
  `summary`, typed `params`, `extra_args` (words), `returns` (words),
  `read_only`, `agent` (`AgentAccess`). The app's own are `doc.*`,
  `app.*` and every keymap command (`app/scripts.rs`); benches register
  theirs in `configure`; packages through `bench_api`.
- **MCP tools** (`app/mcp.rs`): `context` (what is open), `commands`
  (every command, filtered by prefix), `call`, `lua`, `log`, `view` (the
  visible bodies from the camera's direction, 800 × 600, flat shaded,
  through the CPU renderer in `thumbnail.rs`).
- **Instructions** (`app/agent_context.rs`): `ABOUT` and `TOOLS`, the
  user's rules, and the resource `printcad://guide/scripting`
  (`docs/SCRIPTING.md`, generated by `scripts::reference` and checked by
  a test).
- **Geometry queries**: `doc.faces` (kind, a point on the face, area,
  normal, axis, radius, name), `doc.measure` (volume, area, centre,
  bounds), `doc.rebuild` (the features that fail).
- **Scripts**: `lua` answers what the script printed and the error that
  stopped it; its return value is dropped.

## Design

### 1. Notes, examples and recipes

**On the command.** `CommandSpec` gains three fields, set with builder
methods where the command is registered, so the knowledge lives beside
the code it describes:

```rust
pub struct CommandSpec {
    // ...
    /// What an agent must know beyond the arguments: what it refuses,
    /// does silently, or is easily mistaken for; one bullet each.
    pub notes: Vec<String>,
    /// Working uses, each a Lua script and what it shows.
    pub examples: Vec<Example>,
    /// Other commands that do the related thing (`sketch.new` from the
    /// surface steps, `surface.sew` from `surface.fillet`).
    pub see_also: Vec<String>,
}

pub struct Example {
    /// What it shows, one line.
    pub title: String,
    /// A Lua script, run as `lua` runs it, from an empty document.
    pub script: String,
}
```

`CommandSpec::note`, `::example` and `::see_also` add them. Notes are
plain sentences in the voice of the docs; an example ends in `assert`s
on what it made (`#pc.doc.rebuild() == 0`, a `doc.measure` volume, a
face count), so running it checks it.

**Recipes.** Workflows that span commands (a sketch padded and pocketed;
a closed sketch extruded and capped and sewn into a solid; a hole
pattern; a joint driven and recorded) are markdown files under
`docs/recipes/`, each a short text and one or more ```lua blocks. They
are served as documents through `describe` and listed in the index.

**Checked by the suite.** One test (`app_shell`, beside the reference
test) runs, headless, every example of every registered command and
every ```lua block of every recipe, each in a fresh document, through
the same path as `printcad --script` (`headless.rs`). A failure names
the command and the example. The suite's time budget (60 s a program)
bounds it: examples are small parts, and a slow one is marked and run on
request, as a big-model test is.

**In the reference.** `scripts::reference` writes notes, see-also and
the first example of each command into `docs/SCRIPTING.md`, so people
get them too; the drift test keeps it generated.

**Packages.** `bench_api`'s command registration takes the same
`notes`, `examples` and `see_also`; a package's examples run in
`wb_wasm/tests/packages.rs` for the packages in `sdk/`, and a third
party's are its own to test. The index marks a package's commands with
the package's name.

**Where to start.** The notes the Surface report would have needed
first (every `surface.*`, `sketch.new`, `design.pad`/`pocket`/`fillet`/
`hole`, `doc.faces`, `doc.measure`, `doc.rebuild`), then a pass over
each bench. A command with no note is fine; a command whose behaviour
surprised an agent gets one, with an example that shows it.

### 2. Discovery

Three MCP tools join `commands` (which stays, for a whole prefix):

- **`search`** `{queries: [string], limit?}`: for each query, the
  commands and documents it matches best, ranked, each as one line (id,
  summary). Several queries in one call answer in groups, one per query,
  so a broad word cannot crowd out the rest.
- **`describe`** `{keys: [string]}`: each key's full entry: a command
  (summary, arguments, returns, notes, examples, see-also, access), a
  recipe, or a guide section. A key is resolved loosely: a bare name
  (`fillet`) lists the commands it could mean, a typo gets the nearest
  ids suggested, and a key not found says so beside the ones that were.
- **The index.** One line per command (`id`: summary), grouped by
  prefix, put into the instructions an MCP connection opens with: about
  5,000 tokens for today's 245 commands, so an agent knows the whole
  surface from its first turn and calls `describe` for what it uses.

**Ranking.** BM25 over each command's id (split at dots and
underscores), summary, notes and parameter names, and over recipes' titles
and text: words lower-cased, plurals folded, and the query expanded with
a table of CAD synonyms, kept in one place in the `agents` crate:

| A user says | The commands say |
| --- | --- |
| hole, bore, drill | hole, pocket |
| round, blend | fillet |
| bevel | chamfer |
| extrude, extrusion | pad, extrude |
| cut | pocket, groove, boolean |
| shell, hollow | thickness |
| mirror, reflect | mirror |
| array, repeat | pattern |
| revolve, lathe | revolution, revolve |
| sweep, pipe | pipe, sweep |
| join, merge, union | boolean, fuse, sew |
| constraint, dimension | sketch constraint commands |

The table grows as agents' failed searches show what is missing; the
discovery tests keep a list of queries and the command each must rank
first.

**One implementation.** Search, describe and the index live in a module
of the `agents` crate over a plain list of entries (`CommandSpec`s and
documents), so the MCP server, the Lua `help()` and any later in-app
agent use the same code. `agents` stays free of printCAD's commands: the
app hands it the entries.

### 3. The renderer for proof

The `view` tool takes arguments; without any it draws what it draws
today.

```
view {
  view?:      "current" | "iso" | "front" | "back" | "left" | "right"
              | "top" | "bottom" | {azimuth, elevation} | {direction, up?},
  bodies?:    [id],            // only these, framed to them (default: visible)
  highlight?: [{body, faces?: [index or name], edges?: [index], color?}],
  markers?:   [{point, label?}],
  section?:   {origin, normal},
  edges?:     bool,            // face outlines (default true)
  xray?:      bool,            // bodies see-through, highlights solid
  size?:      [w, h],          // default 800 × 600, capped
  annotate?:  bool,            // axis triad, the framed box's sizes
}
```

- **Fixed and framed.** Named views are orthographic, Z-up as the
  default axis preset, and framed to the bounds of what is drawn: the
  same arguments draw the same picture, whatever the user's camera.
  `"current"` keeps today's behaviour.
- **Edges.** Outlines come from each mesh's `edge_ids` segments (the
  kernel's own edges), drawn over the faces with depth, as the viewport
  draws them.
- **Highlights and markers.** Faces by their `doc.faces` index or name,
  in a colour that stands apart from the bodies' own; markers as a dot
  and a label at a world point, so an agent can mark where it thinks a
  hole's centre is and see it.
- **Section.** Everything past the plane is cut away and the cut drawn
  as a flat, darker fill, as the viewport's clipping plane does.
- **Everywhere.** The renderer is `thumbnail.rs` grown into a module
  (`app/proof.rs` or a small crate), pure Rust on the CPU, so it runs in
  the save worker, headless, in tests and, later, in a web build.
- **For scripts too.** A read-only command, `doc.picture{path, …the same
  arguments…}`, writes the PNG, so headless runs and CI can keep
  pictures of what a script made.

A before-and-after diff (what an edit added and took away, coloured) is
left for later; the arguments above leave room for it.

### 4. Script-first work

- **Instructions.** `TOOLS` says: plan the steps, then run them as one
  `lua` script; compute positions with Lua's arithmetic and loops; read
  geometry with `doc.faces`/`doc.edges` inside the script and pick from
  it; end with `doc.rebuild` and return what was made. One `call` is for
  a single step or for the commands that ask the user every time.
- **A script's value.** `lua` answers the script's return value as JSON
  beside what it printed (`{returned, printed}`), so a script hands back
  ids and measurements without printing and parsing them.
- **`doc.edges`** (read-only): a body's edges, each with its index, kind
  (line, circle, other), a point halfway along it, its direction there,
  its length, its two faces' indices, and its name: what fillets,
  chamfers, extends and blends take, found by filtering in a script
  rather than guessed.
- **Picks as world points.** The notes of every command that takes a
  face or an edge say it is found by a point on it (and a direction),
  in world space, as `doc.faces`/`doc.edges` give them; names are
  strings.

## Alternatives considered

- **Notes as markdown files beside the code** (one per command). Easier
  to write at length, but separate from the registration, so a renamed
  or removed command leaves an orphan, and examples in prose are not
  run. Recipes, which span commands, are markdown for that reason.
- **Notes in `extra_args`.** No structure; examples could not be run.
- **Embedding search** (vectors) instead of BM25 and synonyms. Better
  on paraphrase, but needs a model at run time or a precomputed index
  per version; 245 short entries rank well with words and a synonym
  table, and the misses tell us which synonyms to add.
- **The GPU renderer for `view`.** Prettier and faster, but tied to the
  window, the user's frame and a GPU, and absent headless; proof needs
  the same picture everywhere more than it needs speed.

## Risks and open questions

- **Example time.** 245 commands with an example each, run headless,
  must stay inside the suite's budget. Most examples are a sketch and a
  feature (milliseconds); the runner shares one registry and fresh
  documents.
- **Index size.** The index grows with packages. Past about 10,000
  tokens it should carry the prefixes and their counts and leave the
  rest to `search`.
- **Notes going stale in words.** Examples are checked; the sentences
  are not. Keeping notes to what an example shows limits that.
- **Synonym drift.** A synonym that ranks the wrong command first is
  worse than none; the ranking tests pin the expected first answers.

## Milestones

1. **The contract and its check.** `notes`, `examples`, `see_also` on
   `CommandSpec` and in `bench_api`; the examples runner; the reference
   writes them; notes and examples for the Surface commands and the
   commands the report touched.
2. **Discovery.** `search`, `describe`, the index in the instructions,
   the synonym table and its ranking tests; Lua `help()` on the same
   module.
3. **Proof.** `view` with views, framing, edges, highlights, markers,
   section, x-ray and annotation; `doc.picture`.
4. **Script-first.** The instructions, `lua`'s return value,
   `doc.edges`, the pick notes.
5. **Coverage.** Notes and an example for every command an agent may
   run, bench by bench; recipes for the common parts; the guide
   (`docs/AI.md`) says what agents are given.

## Acceptance

- Every example and recipe runs green in the suite, inside the budget.
- For each query in the ranking tests (`"hole"`, `"round the edges"`,
  `"shell a box"`, `"make a surface from curves"`, `"sew"`, …) the
  expected command ranks first.
- `view` with the same arguments draws the same PNG on any camera, and
  highlights the faces it was asked to.
- The Surface workbench test, made again by an agent from the same
  prompt, reaches every case without an undocumented failure: each
  refusal it meets is one a note or an error message names.
